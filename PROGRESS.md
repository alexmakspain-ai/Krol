## Этап 2 — Backend: модели данных, авторизация, CRUD для категорий и расходов

**Статус:** завершён, ждёт подтверждения пользователя для перехода к этапу 3.

**Модели данных** (`backend/app/models/`), по схеме `data-model.mermaid`:
- `User` — id, email (unique), password_hash, created_at
- `Category` — id, user_id (FK → users, `ON DELETE CASCADE`), name, color
- `Expense` — id, user_id (FK → users, `ON DELETE CASCADE`), category_id
  (FK → categories, `ON DELETE RESTRICT`), title, amount, date, created_at
- В SQLite включён `PRAGMA foreign_keys=ON` (иначе FK-constraints не работают)

**Авторизация** (`backend/app/security.py`, `backend/app/deps.py`,
`backend/app/routers/auth.py`):
- `POST /auth/register` — регистрация по email/паролю, пароль хэшируется
  (passlib + bcrypt), проверка на дублирующийся email
- `POST /auth/login` — вход через `OAuth2PasswordRequestForm` (совместимо с
  кнопкой Authorize в Swagger UI), возвращает JWT (`access_token`)
- JWT: `python-jose`, `sub` = id пользователя, время жизни — 24 часа
  (настраивается через `.env`)
- `get_current_user` — зависимость FastAPI, декодирует токен и подгружает
  пользователя; 401 при отсутствии/невалидности токена

**CRUD для категорий** (`backend/app/routers/categories.py`):
- `GET/POST /categories`, `PUT/DELETE /categories/{id}`
- Все операции ограничены `user_id` текущего пользователя (404 для чужих
  категорий)
- Удаление категории с привязанными расходами → 409 (FK `RESTRICT`)

**CRUD для расходов** (`backend/app/routers/expenses.py`):
- `GET/POST /expenses`, `PUT/DELETE /expenses/{id}`
- Изоляция по `user_id`; при создании/обновлении проверяется, что
  `category_id` принадлежит текущему пользователю (400 иначе)
- Валидация: `amount > 0`, `title` обязателен (Pydantic `Field`)
- `GET /expenses` поддерживает `start_date`/`end_date`/`category_id`,
  сортировку (`sort_by`, `order`) и пагинацию (`skip`/`limit`) — задел под
  виджеты диаграммы/таблицы из этапов 4–5

**Миграция:** `backend/alembic/versions/aab50b75bdb3_create_users_categories_expenses_tables.py`
— создаёт таблицы `users`, `categories`, `expenses` с индексами и FK.
Проверена автогенерацией (`alembic revision --autogenerate`) и применением
(`alembic upgrade head`) к чистой БД.

**Проверено (сквозной сценарий через живой сервер, curl):**
- Регистрация двух пользователей, повторная регистрация с тем же email → 400
- Логин по форме (`username`/`password`), неверный пароль → 401
- Доступ к `/categories` без токена → 401
- Создание категории/расхода, изоляция: user2 не видит категории/расходы user1
- user2 не может создать расход с `category_id` от user1 → 400
- Отрицательная сумма расхода → 422
- Обновление расхода, фильтрация по диапазону дат
- Удаление категории с расходами → 409; после удаления расхода — 204
- `/docs` и `/openapi.json` отвечают 200 (Swagger UI доступен)

**Не доделано (сознательно, для следующих этапов):**
- Нет эндпоинта `/auth/me` (профиль текущего пользователя) — добавим при
  необходимости на frontend-этапах
- Нет ограничения количества попыток входа / refresh-токенов — вне рамок ТЗ
- Нет эндпоинтов экспорта CSV/Excel — это этап 6
- Frontend пока не взаимодействует с этими эндпоинтами — этапы 3–5

## Этап 5 — Frontend: круговая диаграмма с фильтром по периоду

**Статус:** завершён, ждёт подтверждения пользователя для перехода к этапу 6.

**Виджет диаграммы** (`frontend/src/app/charts/expenses-chart/`):
- Кольцевая (donut) диаграмма на Chart.js/ng2-charts (`provideCharts(withDefaultRegisterables())`
  добавлен в `app.config.ts`)
- В центре — название, сумма и процент выбранной/топ категории; обновляется
  при наведении на сегмент (`chartHover`) и фиксируется по клику
  (`chartClick`) — реализовано HTML-оверлеем поверх canvas, а не
  Chart.js-плагином (проще и надёжнее для позиционирования)
- Данные — расходы за период, сгруппированные по категориям (агрегация на
  клиенте, т.к. backend не имеет отдельного endpoint'а для агрегатов)
- Независимый фильтр периода: пресеты Неделя/Месяц/Год (по умолчанию —
  Месяц, как требует ТЗ 3.2) + произвольный диапазон — свой, не связан с
  фильтром таблицы
- Легенда под диаграммой — цветной маркер + название категории
  (кастомная HTML-легенда вместо встроенной Chart.js, т.к. нужен точный
  формат «маркер + название» и клик/наведение на элемент легенды тоже
  обновляет центр)

**Переиспользуемые модули** (рефакторинг, затронул и таблицу из этапа 4):
- `frontend/src/app/shared/period.ts` — чистые функции работы с датами
  (`isoDate`, `startOfWeek/Month/Year`, `presetRange`) — вынесены из
  `expenses-table.ts`, теперь общие для таблицы и диаграммы
- `frontend/src/app/shared/period-filter/` — переиспользуемый
  presentational-компонент фильтра периода (кнопки пресетов + свой
  диапазон), используется и в таблице, и в диаграмме
- `ExpensesService.listAllExpenses(range)` — обходит все страницы backend
  (лимит 200/запрос) и возвращает полный список расходов за период; нужен
  диаграмме, т.к. `GET /expenses` ограничен `limit<=200`

**Найден и исправлен баг из этапа 4:** `isoDate()` форматировала дату через
`date.toISOString()` (UTC), а `startOfWeek/Month/Year` строят дату в
локальном времени — при их совместном использовании граница периода
систематически сдвигалась на день назад (в окружении с TZ UTC+2
подтверждено: «месяц» начинался с 31 июля вместо 1 августа). Также
задевало поле «Дата» по умолчанию в форме добавления расхода (`expense-form.ts`)
— «сегодня» могло показывать вчерашнюю дату в первые часы суток. Исправлено:
`isoDate()` теперь строит строку из локальных `getFullYear/getMonth/getDate`.
Проверено вручную через backend: расход за последний день предыдущего
месяца корректно исключается из фильтра «текущий месяц», сегодняшний —
включается.

**Проверено:**
- `ng build`/`ng test` — без ошибок, 2/2 теста проходят
- Границы периодов (`presetRange`/`isoDate`) — проверены отдельным Node-скриптом
  на нескольких датах (включая границу года)
- Агрегация по категориям (сумма, сортировка по убыванию, топ-категория,
  проценты) — проверена отдельным скриптом на синтетических данных
- Backend напрямую: месячный фильтр с исправленными границами возвращает
  ожидаемый набор расходов (включая/исключая пограничные даты)

**Не проверено вживую в браузере:** расширение Claude in Chrome
недоступно в этой сессии — само взаимодействие с диаграммой (наведение/клик
на сегмент, смена периода, легенда) не пройдено визуально. Рекомендовано
проверить самостоятельно на `http://localhost:4200/expenses`.

**Не доделано (сознательно, для следующих этапов):**

## Доработка после этапа 5 — подкатегории, удаление категорий, доработки диаграммы

Внеплановый запрос пользователя поверх завершённого этапа 5 (не входит в
нумерацию 7 этапов из ТЗ).

**Статус:** завершено.

**Подкатегории** (backend):
- `Category.parent_id` — самоссылающийся nullable FK на `categories.id`
  (`ON DELETE CASCADE`), максимум один уровень вложенности (подкатегория не
  может иметь свою подкатегорию — проверяется на backend, 400 при попытке)
- `CategoryOut`/`CategoryCreate`/`CategoryUpdate` — добавлено поле `parent_id`
- Валидация: родительская категория должна принадлежать пользователю и сама
  быть категорией верхнего уровня; нельзя сделать категорию подкатегорией
  самой себя
- Удаление категории с подкатегориями каскадно удаляет пустые подкатегории;
  если у категории или её подкатегории есть расходы — 409 (как и раньше)
- Новая Alembic-миграция (`5226feb3527f`), с batch-режимом для SQLite
  (добавлен `render_as_batch=True` в `alembic/env.py` — SQLite не
  поддерживает `ALTER TABLE ADD CONSTRAINT` напрямую) и именованными
  constraints (добавлена `naming_convention` в `Base.metadata` —
  безымянные constraints, которые генерировал SQLAlchemy по умолчанию,
  падали в batch-режиме с `ValueError: Constraint must have a name`)

**Кастомный дропдаун категорий** (`frontend/src/app/expenses/category-picker/`):
- Заменяет нативный `<select>` в форме добавления расхода и в

## Доработка №5 — конфигурация сборки фронтенда для Vercel

Внеплановый запрос: сравнение с https://papeles-ai.vercel.app показало,
что их фронтенд открывается мгновенно (статика на CDN), а наш — единый
Docker-сервис на Render (free-план), который засыпает после простоя.
Решили разделить хостинг: фронтенд → Vercel, backend+Postgres — остаются
на Render как есть (не трогаем тариф/архитектуру). Не привязана к
нумерации этапов ТЗ.

**Статус:** завершено — фронтенд задеплоен на Vercel, backend на Render
принимает запросы с него, сквозной сценарий (регистрация → логин)
подтверждён пользователем вживую.

**Сделано:**
- `frontend/src/environments/environment.vercel.ts` — новый файл,
  `apiBaseUrl` абсолютный (`https://krol.onrender.com/api`), в отличие от
  относительного `/api` в `environment.prod.ts` (тот работает только пока
  фронтенд и API на одном origin — как сейчас на Render)
- `frontend/angular.json` — новая конфигурация сборки `vercel` (по образцу
  `production`), с `fileReplacements` на `environment.vercel.ts`
- `frontend/vercel.json` — новый файл: `buildCommand` (`ng build
  --configuration vercel`), `outputDirectory` (`dist/frontend/browser`,
  та же папка, что использует `Dockerfile`), SPA-рерайт всех путей на
  `/index.html` (роутинг Angular путевой, не hash-based)
- Существующая конфигурация `production` и `Dockerfile` не тронуты —
  комбинированный деплой на Render продолжает работать как раньше

**Проверено:**
- `ng build --configuration production` и `ng build --configuration
  vercel` — обе без ошибок
- В собранном vercel-бандле (`dist/frontend/browser/main-*.js`)
  подтверждено грепом, что `apiBaseUrl` — абсолютный URL, а не `/api`
- `ng test` — 2/2 теста проходят (правки не затрагивают компоненты)

**Деплой на Vercel (сделано пользователем, с подсказками по ходу):**
- Импорт репозитория через GitHub App Vercel (потребовалось установить
  приложение и явно разрешить доступ к репозиторию — по умолчанию его не
  было в списке)
- Root Directory = `frontend` — с первой попытки был задан с лишним
  пробелом в конце (`"frontend "`), из-за чего билд падал с `The specified
  Root Directory "frontend " does not exist`; после исправления пробела
  и Redeploy — собралось
- `render.yaml` — добавлен `CORS_ORIGINS` (см. изменения кода ниже) с
  доменом `krol-omega.vercel.app` (стабильный алиас проекта) и
  дополнительно фактическим доменом конкретного деплоя
  (`krol-rd5ff7s5e-alexmakspain-ai.vercel.app`), который браузер показал
  в CORS-ошибке при первой проверке — у Vercel есть оба вида адреса,
  стабильный и одноразовый per-deployment
- Применено на Render вручную через Environment tab (добавление
  `CORS_ORIGINS` там триггерит автоматический передеплой) — сработало
  без обращения к Blueprint-синку

**Проверено вживую пользователем:**
- Открытие `https://krol-omega.vercel.app/` — статика грузится мгновенно
  (в отличие от комбинированного Render-деплоя с холодным стартом)
- CORS-ошибка (`No 'Access-Control-Allow-Origin' header`) — воспроизведена
  до добавления env var, исчезла после
- Регистрация нового пользователя и логин через Vercel-фронтенд к
  Render-backend/Postgres — успешно (после того как выяснилось, что
  тестовый email `1@1.123456` невалиден по TLD — это корректное поведение
  `EmailStr`-валидации, не баг)

**Побочно найдено (не исправлено, отдельная задача):** при 422-ошибке
валидации от FastAPI (`detail` — список объектов, не строка) форма
регистрации показывает `[object Object]` вместо текста ошибки — компонент
не разбирает такой формат `detail`. Не связано с хостингом, существовало
и раньше, просто раньше почти всегда отсекалось валидацией на фронте до
отправки запроса.
